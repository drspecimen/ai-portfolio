Case study: DocuChat

The guided bootcamp capstone: a document question-and-answer backend. The class built it in TypeScript; I am rebuilding the same design in Python and FastAPI, the main language of AI engineering, one tested commit at a time.

How a question gets answered

  1. Upload202 Accepted
  2. Background jobCelery worker
  3. Chunk and embed500-token chunks
  4. Vector storepgvector, HNSW
  5. Retrieve and generateRAG or agent
  6. Cited answer[Source N]

Problem

People waste time hunting through long documents, and a chatbot that guesses is worse than no chatbot.

Solution

Answers drawn only from the user's own documents, each one tied to the passage it came from.

AI component

Documents are split by paragraph, line and sentence, then embedded. A question pulls the closest passages above a relevance floor, fits them into a token budget and sends them to the model at temperature 0.1.

My contribution

I am building every layer myself in Python: routes, services and repositories, JWT auth, role-based access, background workers, caching, rate limits, retrieval, the agent and the MCP server, each with tests and CI.

Challenges

Stopping made-up answers: when nothing scores above 0.3, the system says it could not find the answer. Keeping slow AI calls outside database transactions, so a model timeout never holds a connection.

Production safeguards

  • Settings validated at startup; secrets never logged
  • Per-tier rate limits on auth, uploads and chat
  • Retries, backoff and a circuit breaker on model calls
  • Structured logs, metrics and health checks

Agent guardrails

  • At most 10 steps per request
  • 60-second time limit
  • $0.50 cost ceiling per request
  • Only whitelisted tools, every step traced

Design target

A backend that answers with citations, refuses to guess, and controls AI spending with monthly budgets per user tier, prompt versioning, model fallback and an audit log of every AI call.

Engineering approach

Research taught me to measure before I trust. An AI system people cannot rely on is worse than no system, so I set the limits before writing the clever part.

  1. Understand

    Who has the problem, and what they do today.

  2. Design

    Clear layers, so each part can change alone.

  3. Set limits

    Budgets, rate limits and guardrails come first.

  4. Build

    Small pieces, validated at every boundary.

  5. Evaluate

    Accuracy, latency and cost, measured not guessed.

  6. Observe

    Logs and metrics that explain every failure.
